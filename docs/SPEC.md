# judge-desktop 規格（第一部分：Windows 桌面端）

狀態：草案 v0.1（2026-11-08）。本文件是第一階段的設計依據，之後的實作以此為準，變更需同步更新。

## 1. 來源與現況分析

本規格整合三個既有流程，目標是把它們變成「一般使用者可用、可自行設定」的桌面應用程式。

| 來源 | 現有做法 | 可沿用 | 要解決的問題 |
|---|---|---|---|
| `judge_mcp`（fjud_mcp，Python） | 以關鍵字／案號搜尋司法院判決，`export_word.py`、`update_excel.py`、`recovery_pipeline.py` 產出 Excel 與 Word；`Word匯出/` 內有「案件分析」「類型統計」「範本」「彙整表」等成品 | 搜尋與解析邏輯、欄位定義、Excel 版面（轉型正義判決表格式）、分類統計的思路 | 操作依賴命令列與 MCP 客戶端；分類與批次流程靠人工腳本串接 |
| AGY CLI（Antigravity）對話紀錄 | 「Excel 判決書批次整理 Word」「包庇罪判決Word整理」「轉型正義文獻檢視器設計」等任務，以 `case_analyzer` 子代理分群處理 | 「先取得列表 → 分群 → 每群生成綜合分析」的分段流程 | 分群與分析的規則散落在提示詞裡，使用者無法調整 |
| Claude Code 紀錄（`judge-mcp` 專案）與 民法作業流程 | 先由 AI 依「核心目標」決定爬取策略，再呼叫爬蟲取得判決，最後整理成 12 頁左右的法律國考式文書 | 「目標 → 策略 → 爬取 → 整理」的兩段式設計；可指定範圍與長度的文書樣板 | 目前是單次對話流程，無法保存策略、無法重跑、無法套用到其他使用者的目標 |

結論：原本的流程本質上是「**檢索 → 整理為列表 → 分群／綜合分析 → 單一判決精讀**」四段，只是目前由不同工具、不同對話各自完成。桌面端要把四段串成一條可重複執行的管線。

## 2. 三種核心輸出（對齊三個目標）

每一種輸出都對應一組「策略設定」，策略可由 AI 依使用者目標產生，也可由使用者直接設定。

### 2.1 列表生成（對應：轉型正義判決 Excel 格式）
- 輸入：搜尋範圍（法院、案由、日期區間、關鍵字、條文）。
- 篩選策略兩種：
  - **條文為核心**：以「某條文／某法律」為單位，列出所有引用該條文的判決（轉型正義 Excel 的做法）。
  - **條件為核心**：以多個條件的交集／聯集為單位（例如「以下三個關鍵字且非撤銷發回」）。
- 內容範圍：只含基本欄位／含摘要／含全文（全文可選，會增加儲存與耗時）。
- 輸出：Excel（沿用既有版面），可選 Word 版列表。
- 每筆判決可單獨下載 PDF。

### 2.2 綜合分析與分群（對應：民法作業式的「依目標生成策略」＋列表分類）
- 前置：使用者先有一份列表（2.1 的產出），或直接輸入目標。
- 流程：
  1. **目標描述**：使用者用一句話或表單描述研究問題（例：「比較各轉型正義條例對『回復原狀』的認定差異」）。
  2. **策略生成**：AI 產生「檢索策略 JSON」（關鍵字、條文、法院、期間），使用者可審閱、修改後執行。
  3. **爬取**：執行策略，取得判決列表。
  4. **分類**：使用者設定分類維度（預設：條例、法院、結果、爭點），或由 AI 提議分類；分類結果可逐筆修改。
  5. **綜合表**：對每一群產生綜合分析表（欄位可自訂，預設：爭點、認定標準、結論、引用條文），輸出 Excel／Word。
- 分類與欄位的定義存成「專案設定檔」，同一組設定可套用到新的列表。

### 2.3 單一判決精讀（對應：民法作業式文書）
- 輸入：單一判決（以判決字號或 PDF）。
- 使用者設定：關注重點（可多選，例：事實、爭點、理由、主文）、輸出長度（頁數或字數）、文書樣式（法律國考式／研究摘要）。
- 未指定重點時，AI 自行判斷。
- 輸出 Word：摘要段落在前，原文段落在後，原文依重點類型以不同螢光色標示。
- 判決 PDF 的處理見 §4。

## 3. 功能分層：簡單與詳細的平衡

為了同時服務「只想快速得到表格」與「想精細控制」的使用者，採三層設定：

1. **第一層（預設）**：首頁是三張大卡片（列表生成／綜合分析／單一判決）。選定後只問 3 個問題：範圍、輸出格式、是否需要 AI。
2. **第二層（展開）**：每張卡片下的「進階設定」展開，包含分類維度、欄位、長度、顏色規則。
3. **第三層（專家）**：可直接編輯策略 JSON 與 AI 提示詞模板，並可匯入／匯出設定檔。

功能開放原則：凡是「可能因人而異」的選項（分類維度、欄位、顏色、提示詞、輸出長度）都要可設定，但提供預設值，使用者不改也能完成任務。

## 4. 判決 PDF 處理

判決 PDF 分兩類，需要不同的處理：

| 類型 | 特徵 | 處理方式 |
|---|---|---|
| 新式 PDF | 可選取文字（司法院新版系統） | 直接抽取文字，保留段落與條號；原文定位用文字索引 |
| 舊式 PDF | 掃描影像或文字層不完整 | 先轉為影像；OCR（可選，預設關閉，需使用者啟用）；頁面以「每頁 4 格」排版貼入 Word，並在摘要後附原文影像 |

螢光標示：
- 標示對象是「原文段落」，對應到摘要的每一條重點。
- 顏色依重點類型設定（預設：事實＝黃、爭點＝綠、理由＝藍、主文＝粉），使用者可自訂。
- 新式 PDF 可直接以文字標示；舊式 PDF 只能以影像區塊標示，需在規格中明確告知使用者差異。

## 5. 技術選型（建議，待確認）

| 項目 | 建議 | 理由 |
|---|---|---|
| 桌面框架 | **Electron + TypeScript + React** | 與參考專案 `debate-companion-desk` 相同，已有 NSIS 安裝、自動更新、客製安裝流程可以直接參照；無系統選單可用 `Menu.setApplicationMenu(null)` 加自訂標題列 |
| 核心邏輯 | **TypeScript 套件 `packages/core`**（搜尋、解析、PDF、Word／Excel 產出、AI 提示詞） | 遠端 MCP（Firebase Functions）也是 TypeScript，核心可共用，避免兩份實作。舊的 Python 爬蟲在第一階段以 TypeScript 重寫，並以 `judge_mcp` 的測試案例對照結果 |
| Word／Excel | `docx`、`exceljs` | 純 JS，不需要使用者另裝 Office |
| PDF | `pdfjs-dist`（抽文字）、`pdf-lib` 或 `pdfium` 轉影像 | 新舊 PDF 雙路徑 |
| AI | BYOK：Anthropic 原生 API 為一等支援，另支援 OpenAI 相容端點（base_url＋金鑰），金鑰存於 Windows 憑證管理員，見 §10 | 公開散布時不由開發者承擔 AI 費用，也不把金鑰放進安裝檔 |
| 資料儲存 | 本機 SQLite（快取、專案、策略）＋ JSON 設定檔 | 單機使用，不需要伺服器 |
| 更新 | `electron-updater` + GitHub Releases；熱修復採「只更新 `app.asar` 內的前端資源」 | 與參考專案一致；熱修復只用於 UI／提示詞，核心變更仍需完整更新 |
| 發版 | GitHub Actions：push tag → 建置 → 簽章（若有憑證）→ 建立 Release → 上傳安裝檔與 `latest.yml` | 自動化 |
| 安裝 | NSIS 客製：自訂安裝路徑、解除安裝時可選擇保留資料、無系統選單 | 客製化需求 |

爬取執行位置：**預設在使用者電腦上執行**（使用者 IP、無伺服器成本、降低對司法院系統的集中請求）。遠端 MCP 只在需要時呼叫同一套核心（見 `judge-remote-mcp`）。

## 6. UI 與視覺語言

- 原生桌面應用的外觀：自訂標題列（最小化／最大化／關閉）、左側導覽、主內容區、底部狀態列；不使用系統選單列。
- 響應式：視窗寬度 < 900px 時導覽收合為圖示列；字級與間距使用 CSS 變數。
- 視覺語言以設計 token 管理（顏色、字級、間距、圓角），深色模式以開關切換，預設跟隨系統。
- 不照抄 `debate-companion-desk` 的版面，只沿用其 token 與安裝／更新的工程做法。
- 使用者面向的文字以繁體中文為主，程式碼與設定鍵名以英文。

## 7. 使用者資料與安全

- 不在程式內嵌任何 API 金鑰；AI 金鑰由使用者輸入，存於 Windows 憑證管理員。
- 檢索結果與判決全文只存本機。
- 若日後啟用遠端 MCP，只能讀取使用者自己的專案與授權範圍，不得讀取其他人的資料。
- 所有外部請求（司法院、AI 服務）都在設定頁可見並可關閉。

## 8. 分階段計畫

1. **Phase 1（本階段）**：規格、repo 結構、核心套件骨架、列表生成（2.1）的最小可用版本，驗證與 `judge_mcp` 相同查詢的結果一致。
2. **Phase 2**：綜合分析（2.2）、AI 策略生成、分類與綜合表。
3. **Phase 3**：單一判決精讀（2.3）、PDF 新舊雙路徑、螢光標示。
4. **Phase 4**：安裝檔、自動更新、熱修復、GitHub Actions 發版。
5. **Phase 5**：遠端 MCP 串接（見 `judge-remote-mcp/docs/SPEC.md`）。

## 10. 決策紀錄

### 2026-11-08：金鑰與爬取位置
- **爬取在使用者電腦執行**，不放雲端。原因：(1) 雲端 IP 可能被司法院網站限制；(2) 全文回傳到雲端會產生下行流量費（GCP 網路出口），本地執行則沒有此費用；(3) 雲端長任務受 HTTP 逾時限制。
- **AI 金鑰**：
  - 一等支援 Anthropic 原生 Messages API（PDF、引用、思考、快取都需要原生介面；Anthropic 的 OpenAI 相容層只適合測試）。
  - 通用支援「OpenAI 相容」設定：`base_url` + 金鑰 + 模型名稱。可用於 OpenAI、OpenRouter、Gemini 的 OpenAI 相容端點、DeepSeek、Ollama 等。需要 JSON 結構化輸出的功能，使用前要以各供應商實測。
  - 金鑰只存 Windows 憑證管理員，設定一次後不需再輸入；設定時做一次測試呼叫確認可用。
- **不採用的做法**：
  - 不使用使用者的 Claude／ChatGPT 訂閱登入來代替 API 金鑰。Anthropic 的條款禁止第三方工具使用訂閱憑證（2026 年已有實際封鎖），不可作為預設方案。
  - 若日後要「使用者不用自備金鑰」，只能採用「由專案方代持金鑰並向使用者收費」的代理服務模式，這會讓專案方成為轉售者（需要金流、條款、濫用防護與隱私揭露），屬於另一個獨立決策，暫不實作。
